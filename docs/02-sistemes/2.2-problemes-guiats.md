# 2.2. Problemes guiats (Guides)

> Autor d'aquesta documentació: **Edgar**

## Què és

Un problema "guiat" és un problema que, a més de l'enunciat, ofereix un **botó ben visible** que
duu a una explicació de com abordar-lo: quina estratègia general fer servir, en quins paranys
habituals no caure, i (opcionalment) un esquelet de codi en un llenguatge de programació concret.
**No és la solució**: mai s'hi revela la resposta concreta ni les dades reals que el problema
demana calcular — només la tècnica.

Es pensa sobretot per als problemes "d'introducció": el primer problema de cada tècnica (el primer
de bucles, el primer d'arrays, el primer de fitxers...), perquè un alumne que arriba per primera
vegada a una tècnica tingui on agafar-se sense haver de demanar-ho a un professor.

## Disseny: "guiat" no és una categoria separada

Un problema **és** guiat si i només si té un objecte `Guide` associat — no hi ha cap etiqueta ni
categoria nova (`ProblemType`/`ProblemGroup`) que calgui mantenir sincronitzada a part. Això evita
l'inconsistència de tenir un problema etiquetat "d'introducció" però sense contingut, o amb
contingut però sense etiqueta.

## Model de dades (`judge/models/problem.py`)

Calcat, deliberadament, del patró ja existent `Solution`/`ProblemTranslation` (l'editorial i les
traduccions de l'enunciat):

```python
class Guide(models.Model):
    problem = models.OneToOneField(Problem, related_name='guide', on_delete=CASCADE)
    is_public = models.BooleanField(default=True)
    content = models.TextField(blank=True)   # contingut per defecte / de resguard

    def is_accessible_by(self, user):
        if self.is_public:
            return True
        return self.problem.is_editable_by(user)

    def resolve_general(self, language): ...
    def resolve_runtime_hint(self, runtime, language=None): ...


class GuideTranslation(models.Model):
    problem = models.ForeignKey(Problem, related_name='guide_translations', on_delete=CASCADE)
    language = models.CharField(max_length=7, choices=settings.LANGUAGES, blank=True)   # '' = qualsevol idioma
    runtime = models.ForeignKey(Language, null=True, blank=True, on_delete=CASCADE, related_name='+')  # None = qualsevol llenguatge de programació
    content = models.TextField()

    class Meta:
        unique_together = ('problem', 'language', 'runtime')
```

`Language` aquí és el mateix model que ja representa els llenguatges de programació de tot el jutge
(Python 3, Java 11, C++17...) — el mateix que fa servir `Profile.language` (el llenguatge de
programació preferit d'un alumne) o `LanguageLimit`.

### Els dos eixos independents

Una guia es pot adaptar per **dos eixos, independents entre si**:

1. **Idioma de la interfície** (`language`: ca/en/es...) — l'explicació textual de l'estratègia.
2. **Llenguatge de programació** (`runtime`: Python 3, Java 11...) — l'esquelet de codi.

Cada `GuideTranslation` pot deixar **qualsevol dels dos** en blanc per dir "vàlid per a qualsevol
valor d'aquest eix". Per exemple, si l'Edgar (com a professor) escriu:

- `language='ca', runtime=Python3` → una explicació en català amb codi Python.
- `language='ca', runtime=None` → una explicació en català vàlida per a qualsevol llenguatge.
- `language='', runtime=Java11` → un esquelet de codi Java, vàlid amb qualsevol idioma d'interfície.

...el mètode `Guide.resolve_general(language)` cerca les traduccions **sense** llenguatge de
programació (`runtime__isnull=True`) que coincideixin amb l'idioma demanat (o que siguin genèriques,
`language=''`), i es queda amb la més específica; si no en troba cap, cau al `Guide.content` per
defecte. `Guide.resolve_runtime_hint(runtime, language)`, en canvi, busca **només** per `runtime`
—deliberadament, **ignora l'idioma de la interfície**: el codi és útil independentment de si
l'Edgar llegeix la pàgina en català o en castellà, i limitar-lo per idioma feia que un alumne amb
la interfície en castellà es quedés sense veure cap codi (vegeu més avall, "Bug detectat").

### Per què dues consultes separades i no una de sola

La pàgina de la guia mostra **sempre** les consideracions generals (l'estratègia, sense codi) i, a
sota, **si n'hi ha**, l'esquelet de codi pel llenguatge de programació seleccionat — mai l'un en
lloc de l'altre. Per això calen dos mètodes de resolució independents (`resolve_general` i
`resolve_runtime_hint`) en comptes d'un de sol que retorni "la millor coincidència" (que amagaria
l'explicació quan es tria un llenguatge de programació, o el codi quan l'idioma no coincideix).

### La restricció que MySQL no aplica

`unique_together=('problem','language','runtime')` evita duplicats exactes... excepte quan
`runtime` és `NULL`: MySQL/MariaDB tracta cada `NULL` com a diferent als efectes d'un índex únic
(a diferència d'altres motors de BD), de manera que dues files amb `runtime=NULL` i el mateix
`problem`+`language` **no** es detecten com a duplicades pel constraint de BD. Per això
`GuideTranslation.clean()` fa la comprovació explícitament en Python i llença `ValidationError`
també en aquest cas.

## Com es tria el llenguatge de programació

`ProblemGuide` (`judge/views/problem.py`) decideix el `runtime` a mostrar amb aquesta prioritat:

1. Paràmetre explícit a la URL: `?runtime=<key>` (p. ex. `?runtime=PY3`), o `?runtime=none` per
   forçar només les consideracions generals (desactivant l'autodetecció).
2. Si l'usuari ha iniciat sessió: el seu llenguatge de programació preferit
   (`request.profile.language_id`, el mateix camp "Llenguatge" de `/edit/profile/`).
3. Si no hi ha cap dels dos anteriors: cap (només es mostren les consideracions generals).

La pàgina de la guia mostra un selector ("Show code for: General considerations | Python 3 | Java
11 | ...") amb totes les combinacions de llenguatge de programació que tenen contingut per a aquest
problema concret (`Language.objects.filter(id__in=problem.guide_translations...)`), perquè l'alumne
pugui canviar-hi manualment.

## Bug detectat i corregit durant el desenvolupament

La primera versió acoblava els dos eixos en una sola consulta (calia coincidir idioma **i**
llenguatge de programació alhora). Com que totes les traduccions es van escriure només en català,
un alumne amb la interfície en castellà que triava "Python 3" no veia cap codi: la consulta no
trobava cap fila i queia directament al contingut genèric sencer, **perdent també l'explicació
general** (es mostrava l'un o l'altre, mai els dos). El propi usuari ho va detectar provant la
funcionalitat; es va corregir separant els dos mètodes de resolució com s'explica més amunt.

## Permisos i visibilitat

- **`Guide.is_public=True`** (per defecte): visible per a qualsevol usuari que pugui veure el
  problema — a diferència de l'editorial (`Solution`), una guia **no és un "spoiler"** de la
  solució, així que no cal amagar-la fins que l'alumne l'hagi resolt.
- **`Guide.is_public=False`**: només visible per a editors del problema (`problem.is_editable_by`).
- **Amagada durant concursos** (`request.in_contest`): mateix criteri que l'editorial, per evitar
  donar avantatge durant una prova puntuable.

## Marcatge visual

- **Pàgina del problema** (`templates/problem/problem.html`): etiqueta "Introducció" al costat del
  títol, i un botó gran i molt destacat ("Llegeix la guia", color `--highlight_blue`) **per sobre**
  del botó "Submit solution" — deliberadament més cridaner que la resta d'enllaços de la barra
  lateral (que són text pla).
- **Llistes de problemes i de tasques** (`templates/problem/list.html`, `templates/problem/task.html`):
  fila ressaltada (`intro-problem-row`) i una icona de birret (Font Awesome `fa-graduation-cap`) al
  costat del nom.
- Per evitar consultes N+1 a les llistes (accedir a `problem.guide` directament des d'una plantilla
  Jinja2 llençaria una excepció per a cada problema sense guia — una relació *OneToOne* inversa
  sense fila corresponent no torna `None` silenciosament, com sí que fa Django Template Language),
  les consultes de llista fan `.annotate(has_guide=Exists(Guide.objects.filter(problem_id=OuterRef('pk'))))`
  i la plantilla comprova `problem.has_guide` (un booleà pla, segur d'usar sempre).

## Vista i URL

- `ProblemGuide` (`judge/views/problem.py`) — `/problem/<code>/guide` (`dmoj/urls.py`).
- Plantilla `templates/problem/guide.html`, amb el mateix renderitzat Markdown que l'editorial
  (`|markdown('problem', MATH_ENGINE)|reference|str|safe`).

## Administració

Al panell d'administració de Django, dins la fitxa d'un problema (`ProblemAdmin`), hi ha dos
`inline` nous al costat dels ja existents d'editorial i traduccions:

- **Guide** (`is_public`, `content`) — l'explicació per defecte, amb editor Markdown.
- **Guide translations** (`language`, `runtime`, `content`) — tantes files com combinacions
  d'idioma/llenguatge de programació es vulguin oferir.

## Selecció inicial de problemes guiats (procés, no codi)

Es va decidir cobrir primer, dins la categoria de problemes "Introduccio" (154 problemes, un cop
retirats els d'examen — vegeu més avall), **els 3-4 problemes de menys punts de cada tipus**
(`ProblemType`: Bucles simples, Arrays, Strings, Sense Bucles, Matemàtiques, Fitxers de text,
Estructures de Dades, Matrius, Ordenació, Jocs, Geometria, Recursivitat, Hash, Grafs...) — la idea
és que siguin els problemes que un alumne toca primer de cada tècnica, no necessàriament els que
tenen menys punts en absolut. Això va donar una selecció inicial de 40 problemes.

Es va crear, de pas, una categoria nova `ProblemGroup` **"Examens"**, i s'hi van moure els 11
problemes que tenien "Examen" al nom (que abans estaven barrejats dins "Introduccio") — no té
sentit oferir una guia d'aprenentatge a un exercici pensat per avaluar, no per ensenyar.
